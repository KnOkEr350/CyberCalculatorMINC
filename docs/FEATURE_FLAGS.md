# Feature flags

Новые модули ТЗ 4.4 поставляются выключенными и включаются в конфигурации VM без пересборки образов.

## Конфигурация

В `.env` используются два независимых списка через запятую:

```dotenv
BACKEND_FEATURE_FLAGS=teachers,oop_rpd
FRONTEND_FEATURE_FLAGS=teachers
```

В этом примере API преподавателей и ООП/РПД разрешены на backend, но пользователям показан только экран преподавателей. После изменения `.env` необходимо пересоздать `backend` и `worker`. Frontend получает актуальный набор через `GET /api/features`; пересборка статического контейнера не требуется. Backend и frontend настраиваются независимо, поэтому оператор включает frontend-экран только вместе с требуемым backend-флагом.

Все флаги выключены по умолчанию. Неизвестное имя считается ошибкой конфигурации и блокирует запуск процесса. Значение `all` включает все известные флаги и допускается только на тестовом стенде. Отключённый backend-модуль не регистрирует свои маршруты и отвечает `404`; frontend при недоступности конфигурации скрывает все экраны. Если ни один frontend-флаг не включён, после входа показывается диагностическое состояние «Модули не включены».

## Подключение backend-модуля

Модуль передаётся в composition root через условный registrar или получает типизированные options для независимых групп маршрутов:

```go
routing.When(cfg.BackendFeatureFlags.Enabled(featureflags.Teachers), teachers.New(db))
```

Регистратор и его тесты разрабатываются внутри предметного модуля. Изменение списка в `server/routes.go` выполняет интеграционный поток.

## Подключение frontend-экрана

Каждый descriptor экрана получает стабильное имя флага, после чего registry фильтруется общей функцией:

```js
const visibleScreens = CyberCalcFeatures.filter([
  { id: "dashboard", render: renderDashboard },
  { id: "teachers", featureFlag: "teachers", render: renderTeachers },
]);
```

Перед авторизованным bootstrap и построением первой навигации frontend ожидает `CyberCalcFeatures.ready`. Router и lazy loader повторно проверяют доступность descriptor, поэтому прямой переход на выключенный экран не обходит флаг.

Общие API регистрируются как зависимости включённых возможностей. Например, любой предметный экран включает общий реестр `/api/entries`, документы и справочники партнёров, а `teachers` дополнительно включает справочник сотрудников и ОКЗ. Это не включает соседние dashboard/reporting/settings endpoints.

## Выкладка на прод

При ручной выкладке флаги берутся из `.env` на сервере (пример — `.env.example`, в нём включены все модули), см. раздел «Ручная выкладка на сервер» в `docs/RUNBOOK.md`; `deploy-safe.sh` в конце сам запускает проверку флагов.

Деплой-задача CI (`.github/workflows/ci-cd.yml`) сама включает все модули ТЗ 4.4 явным списком в `BACKEND_FEATURE_FLAGS` и `FRONTEND_FEATURE_FLAGS`; переменные репозитория `PROD_BACKEND_FEATURE_FLAGS` и `PROD_FRONTEND_FEATURE_FLAGS` переопределяют список без правки кода. Значение `all` в выкладке не используется: в production оно запрещено. Тест `featureflags/deploy_config_test.go` следит, чтобы каждый флаг реестра был включён в выкладке и проверялся.

После выкладки `scripts/verify-deployment.sh` сверяет конфигурацию с фактом: `/api/features` должен сообщать каждый включённый для фронтенда флаг, а маршрут каждого включённого модуля без входа отвечать 401 (404 — модуль не подключён). Пустой `BACKEND_FEATURE_FLAGS` выводит предупреждение.

Режим `APP_ENV` задаётся переменной `PROD_APP_ENV` (по умолчанию `development`). Для `production` заранее нужны `PROD_PUBLIC_URL=https://…`, `PROD_CLAMAV_ADDRESS`, уникальные пароли и второй фактор для пользователей: без них приложение не стартует, поэтому переход выполняется отдельно и проверяется шагом «Validate deployment settings».
