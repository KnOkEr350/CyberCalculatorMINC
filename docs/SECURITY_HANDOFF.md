# Передача владельцу CI/CD

Папка `.github` восстановлена целиком до `b89e92c` («добавление всего нового»), родителя `cf24da4` («рбпо»). Добавленные в «рбпо» обязательные проверки и Dependabot убраны из этой папки. Код приложения, миграции, Dockerfile, Compose и эксплуатационные скрипты с исправлениями безопасности не откатывались. Настройки branch protection на GitHub не менялись: если обязательные статусы настроены там отдельно, их должен проверить владелец репозитория.

## Что нужно согласовать до следующего деплоя

- После запуска CI/CD №22 smoke-запросы POST/PUT дополнены `X-Cybercalc-Request: 1`: без него текущий API отвечал HTTP 403 на входе, job `verify` завершался ошибкой, а зависимый deploy пропускался. CSRF-защита приложения не отключалась. Браузерный клиент также передаёт заголовок.
- Старый workflow сам не передаёт новые настройки безопасного production-развёртывания. Нужно проверить фактическую конфигурацию хоста/Compose: `APP_ENV=production`, `PUBLIC_URL=https://домен`, доступный `CLAMAV_ADDRESS`, постоянный секрет `MFA_ENCRYPTION_KEY` (32 случайных байта в Base64), уникальный сильный `DB_RUNTIME_PASSWORD` и bootstrap-пароль. Без `APP_ENV=production` по умолчанию используется development, а отсутствие адреса антивируса означает отсутствие сканирования.
- Внешний TLS-прокси и антивирус должны быть настроены отдельно. Ключ MFA нельзя пересоздавать при каждом деплое: существующие секреты зашифрованы им. Ключ нужно резервировать отдельно и безопасно.
- Миграции выполняются отдельным сервисом `migrate`; backend использует ограниченную роль БД. Не подменять её владельцем базы ради обхода ошибок запуска. Проверить доступность секретов мигратора и runtime-роли, резервную копию БД и тома вложений до обновления.

Кроме исправления CSRF-заголовков, это список необходимых согласований, а не внесённые изменения workflow. Совместимость smoke-проверки исправлена локально; фактическую готовность production можно подтвердить только следующим успешным запуском на Debian с корректными настройками хоста.

## Дополнительные исправления приложения после «рбпо»

- Вход повторно проверяет состояние пользователя под блокировкой строки. Проверка MFA, расходование резервного кода, аудит и выдача сессии атомарны; cookie устанавливается только после успешного commit. Logout сообщает об ошибке удаления сессии из БД.
- Сохраняется не более пяти сессий пользователя. Лимит попыток входа по email остаётся 12 за 15 минут; общий лимит по непосредственному сетевому узлу поднят со 100 до 600, поскольку за reverse proxy он общий для клиентов. Проверка узла выполняется первой, чтобы ограничить создание счётчиков для произвольных email. Клиентским `X-Forwarded-For` приложение не доверяет.
- Незавершённая настройка MFA сбрасывается при смене пароля. Начало настройки проверяет, что пароль и состояние учётной записи не изменились во время проверки.
- Сохранение и проверка вложений ограничены корнем хранилища, включая защиту от выхода через символические ссылки. Сканирование происходит до короткой транзакции метаданных; квота сериализована по пользователю, права перепроверяются перед сохранением.
- Клиент ClamAV читает ответ до NUL, не ждёт закрытия соединения и прерывается при отмене запроса.

При ошибке commit загрузки результат может быть неизвестен: сначала нужно обновить список вложений, затем решать о повторной загрузке. Файлы в этой ситуации намеренно не удаляются автоматически, чтобы не повредить уже сохранённые записи. Возможные непривязанные файлы требуют сверки с БД и очередью удаления; автоматическая уборка таких файлов в этом изменении не реализована.

Эти изменения не являются гарантией отсутствия всех уязвимостей. Проверки исходников и изолированные интеграционные тесты не заменяют проверку реальных production-секретов, TLS, антивируса, восстановления резервных копий и настроек GitHub владельцем инфраструктуры.

## Выполненные локальные проверки

Нативный Go 1.27.1: `go test -race -count=1 -timeout=120s ./...` с обеими интеграционными БД, `go vet ./...`; дополнительно `node --check frontend/app.js` и `git diff --check`. Все проверки прошли. Интеграционные тесты использовали отдельные временные базы на уже работающем тестовом PostgreSQL, без пересборки или перезапуска контейнеров. Регрессионные проверки включают гонку входа с отключением пользователя, откат и ограничение сессий, создание файлов через символические ссылки, NUL-ответы ClamAV и отмену сканирования. Реальный production-деплой и действующий сервис ClamAV этим прогоном не проверялись.
