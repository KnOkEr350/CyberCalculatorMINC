# Архитектура CyberCalculatorMINC

## Выбранный стиль

Система — **модульный монолит** с отдельными HTTP- и worker-процессами.
Домен, команда и нагрузка пока не обосновывают сетевую и операционную
сложность микросервисов. Границы модулей при этом позволяют выделить
сервис позже, если появится измеримая причина.

```text
Браузер
   |
 nginx (edge, единая точка входа)
   |-- /        -> frontend (immutable HTML/CSS/JS)
   `-- /api/*   -> backend x N (stateless HTTP)
                         |-- PostgreSQL (source of truth)
                         `-- uploads_data (documents)

 worker (scheduled jobs) ---- PostgreSQL / uploads_data / official registries
 migrate (one-shot) --------- PostgreSQL owner connection
```

## Ответственность компонентов

| Компонент | Отвечает за | Не отвечает за |
|---|---|---|
| `nginx` | Входящий HTTP, маршрутизация, балансировка | Бизнес-логика |
| `frontend` | Статический UI | Авторизация и обязательная валидация |
| `backend` | API, аутентификация, авторизация, бизнес-правила | Миграции и задачи по расписанию |
| `worker` | Retention, синхронизация и обогащение справочника | Обслуживание HTTP |
| `migrate` | Версионированные SQL-миграции, выдача прав runtime-роли | Долгоживущая работа |
| PostgreSQL | Транзакции, целостность, аудит, блокировки | Хранение самих файлов |

Go-пакеты также разделены по ответственности: `handlers` завершают HTTP-
операции, `calculators` содержат формулы, `auth` — механизмы аутентификации,
`dbx` — инфраструктуру БД, `workers` — жизненный цикл фоновых задач.

## Надёжность и эксплуатация

- `GET /api/live` проверяет, что HTTP-процесс жив, и не зависит от БД.
- `GET /api/ready` проверяет готовность обслуживать трафик, включая PostgreSQL.
- `GET /api/health` оставлен как совместимый alias readiness-проверки.
- HTTP-реплики stateless; сессии и данные находятся в PostgreSQL.
- Worker один; PostgreSQL advisory locks защищают от дублирования задач при
  ручном запуске или ошибочном масштабировании.
- Миграции выполняет отдельный one-shot контейнер с owner-ролью; API и worker
  используют ограниченную runtime-роль.
- Деплой проверяет точную версию frontend и readiness API. Откат восстанавливает
  образы и окружение `backend`, `worker`, `frontend`, `nginx`; миграции назад не откатываются.
- HTTP-журнал содержит request ID, метод, путь, статус, размер ответа и длительность.

## Границы масштабирования

В одном Docker-хосте API масштабируется горизонтально. Для перехода на несколько
хостов сначала нужно заменить POSIX volume `uploads_data` на объектное хранилище,
вынести PostgreSQL в управляемый HA-кластер и добавить распределённый edge/LB.
Разделение Go-кода на микросервисы до этого не устраняет ни одно из этих ограничений.

## Архитектурные правила

1. Валидация и контроль доступа обязательны на backend; UI не является границей доверия.
2. Данные домена изменяются транзакционно, с внешними ключами и аудитом.
3. Долгие и плановые задачи не запускаются в HTTP-репликах.
4. Новая сетевая граница добавляется только при независимом масштабировании,
   отдельном владении или измеримой изоляции сбоев.
5. Любое изменение контракта проходит unit/contract-тесты и Compose smoke test.
