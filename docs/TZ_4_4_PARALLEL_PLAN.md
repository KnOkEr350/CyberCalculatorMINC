## 1. Основные принципы

1. Сначала фиксируются контракты, затем независимо реализуются backend, frontend и тесты.
2. Новые предметные данные хранятся в типизированных таблицах. `entries.payload` остаётся временным слоем совместимости и не расширяется новыми полями ТЗ 4.4.
3. Каждая функциональная область получает собственные:
   - SQL-миграции;
   - Go-пакет домена;
   - HTTP-маршруты;
   - frontend-модуль;
   - unit/contract/integration-тесты.
4. Общие файлы не редактируются несколькими командами одновременно. Подключение модулей выполняет отдельный интеграционный поток.
5. Все новые возможности включаются feature flags до завершения миграции старых данных.
6. PostgreSQL принимается основной СУБД до отдельного решения по SQLite/SQLCipher.
7. Все деньги хранятся как `NUMERIC`, в Go используются целочисленные копейки или существующий `money.Amount`.
8. Официальный отчёт формируется только из утверждённых и регуляторно допустимых данных.
9. Risk Engine является внутренней аналитикой системы: риск вычисляется, не редактируется вручную и не подменяет readiness, eligibility или approval.
10. Нормативные формы и тарифы версионируются по официально опубликованным актам. Локальный `tz/Приказ_270_2026_fin.docx` нельзя превращать в golden source до сверки его реквизитов и контрольной суммы с официальной редакцией.
11. Отсутствие профильного исполнителя не оставляет задачу бесхозной: применяется контролируемый fallback к куратору по ADR-22 без неявного расширения permissions.

### 2.1. Межмодульные контракты

Эти контракты утверждаются до реализации вертикальных модулей. Команды могут начинать работу с fake-реализациями интерфейсов, не ожидая готовности соседнего потока.

| Контракт | Минимальное содержание | Потребители |
|---|---|---|
| `ActivityProjection` | activity/tenant/partner/agreement/kind/year/slice, units, plan, calculated fact, confirmed fact, counted fact, readiness, eligibility | Дашборд, отчёты, `.pkg`, snapshots |
| `APIEnvelope` | `items`, `total`, `limit`, `offset`, `aggregates`, `permissions`; структурированные field errors и request ID | Все frontend-экраны |
| `OptimisticMutation` | `version` или `If-Match`; `409 VERSION_CONFLICT`; idempotency key для команд | Все изменяемые реестры |
| `ReadinessResult` | state, blocking reasons, warnings, checks, ruleset version, evaluated_at | Все мероприятия и UI |
| `DocumentService` | typed document link, blob hash, MIME, size, author, review state, permissions | Все домены, CAS, отчёты |
| `ReportJob` | code, format, parameters, queued/running/ready/failed/expired, result hash | Экран отчётности и все генераторы |
| `Clock/Calendar` | `Now`, `AddDays(policy)`, `ReportingCutoff`; fake clock для тестов | Таймеры, snapshots, workflow |
| `CAS` | `Put/Open/AddRef/ReleaseRef/Verify/GC`; SHA-256 исходных байтов, zstd как внутренняя деталь | Документы, backup, audit |
| `CryptoEngine` | EncryptForRecipients/Decrypt/Sign/Verify, key/certificate references, typed errors, provider factory; private keys не проходят через БД | `.pkg`, snapshot seals, backup |
| `PackagePayload` | format/schema version, package/sender/recipient IDs, signer/recipient key IDs, algorithms, scope, stable records, revisions, tombstones, decimal amounts | Экспорт, импорт, Diff Engine |
| `DiffResult` | identical/changed/local-only/remote-only/conflict, local/incoming values, stable decision key | UI сверки, commit, протокол |
| `AuditEvent` | actor/role/tenant/request/action/entity/old/new/reason/prev_hash/hash | Все mutation и системные jobs |

Деньги во внешних контрактах передаются десятичной строкой или целым количеством копеек, но не JSON `float`. Даты передаются как `YYYY-MM-DD`, время — RFC 3339 UTC с явно определённым business timezone на уровне правил.

## 12. Файлы, CAS и Audit Trail

## 19. Definition of Done для каждого пакета

Пакет считается завершённым, только если:

1. Контракт и ограничения предметной области зафиксированы.
2. Миграция идемпотентно применяется на пустую и существующую БД.
3. Есть backend-валидация; UI-валидация не является границей доверия.
4. Tenant scope и RBAC покрыты негативными тестами.
5. Все изменения создают audit event.
6. Денежные вычисления не используют `float64` на границе хранения.
7. Есть unit и integration tests, а для API — contract tests.
8. Обновлена трассировка требований.
9. Старые данные либо мигрированы, либо явно отмечены как требующие уточнения.
10. `go test ./...`, frontend tests, migration tests и `git diff --check` проходят.
11. Feature flag может безопасно выключить незавершённую возможность.
12. Документация пользователя и оператора обновлена.

## 20. Минимальный состав команды для высокой параллельности

При наличии 12–16 разработчиков разумно выделить:

- 2 человека: core/data/contracts;
- 1: security/RBAC;
- 1: storage/audit;
- 1: crypto/diff;
- 1: workflow/snapshots;
- 4–5: доменные модули;
- 3–4: frontend-экраны;
- 2: reporting;
- 1–2: platform/appliance;
- 2 QA/SDET, работающих параллельно с разработкой.

При меньшей команде пакеты сохраняются, но один разработчик последовательно берёт несколько независимых пакетов. Объединять пакеты обратно в монолитные задачи не рекомендуется.
