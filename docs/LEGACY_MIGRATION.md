# Стратегия legacy migration

Документ закрывает BASE-11 и конкретизирует принятое
[ADR-10](adr/ADR-10-legacy-migration.md). Он обязателен для всех переходов от
`entries.payload` и других legacy-структур к типизированным доменным таблицам.
Правила именования и неизменности SQL-файлов задаёт
[MIGRATIONS.md](MIGRATIONS.md).

## Инварианты сохранности

На всём переходе выполняются следующие условия:

1. Legacy-строка не удаляется и не изменяется backfill-задачей. Типизированная
   строка хранит `legacy_entry_id` с уникальным ограничением.
2. Dual-write выполняется одной транзакцией. Успех только одной записи из двух
   считается ошибкой и полностью откатывается.
3. Повторный backfill идемпотентен: используется `INSERT ... ON CONFLICT
   (legacy_entry_id) DO UPDATE`, а результат зависит только от исходной строки
   и версии mapping.
4. Неоднозначные значения не угадываются. Они записываются в очередь ручного
   разбора с кодом причины, tenant, legacy ID и безопасным снимком полей.
5. Деньги сравниваются как `NUMERIC`/копейки, даты — как календарные даты,
   идентификаторы, автор и `created_at` сохраняются без округления и подмены.
6. Документы и связи не копируются по пути хранения: типизированная запись
   ссылается на тот же blob/attachment ID, а сверка проверяет hash и размер.
7. Каждый запуск backfill, reconciliation, cutover и rollback имеет
   `request_id` и событие аудита по контракту BASE-10.

## Состояния домена

Каждый домен (`teachers`, `ood_rpd`, `internship`, `employment_practice`,
`top_it`, `minc_decision`, `schools`) проходит состояния независимо.

| Состояние | Чтение | Запись | Условие перехода |
|---|---|---|---|
| `legacy` | legacy | legacy | Зафиксированы mapping и владелец |
| `dual_write` | legacy | legacy + typed в одной транзакции | Схема применена, contract-тесты зелёные |
| `backfill` | legacy | dual-write | Worker идемпотентен и возобновляем |
| `shadow_read` | legacy; typed только сверяется | dual-write | Backfill покрыл все классифицированные строки |
| `typed_read` | typed | dual-write | Два последовательных reconciliation без необъяснённых расхождений |
| `typed_only` | typed | typed | Два успешных отчётных цикла и отдельное решение о cutover |
| `retired` | typed | typed | Истёк срок совместимости; удаление оформлено отдельной миграцией |
| `rolled_back` | legacy | dual-write | Сработал критерий rollback |

Переходы с пропуском состояний запрещены. Состояние и версия mapping хранятся
в конфигурации/feature flags отдельно для каждого домена; глобального флага,
который переключает все виды мероприятий одновременно, быть не должно.

## 1. Подготовка схемы

В PR домена должны находиться:

- additive SQL-миграция в закреплённом диапазоне и запись checksum;
- `legacy_entry_id UUID UNIQUE NOT NULL` либо эквивалентный стабильный ключ;
- версия mapping и таблица кодов ручного разбора;
- typed repository, legacy adapter и единая доменная валидация;
- метрики dual-write и shadow-read с доменом и tenant, но без персональных
  данных в label;
- тест upgrade со старой схемы и повторного запуска миграций.

DDL сначала только добавляет таблицы, столбцы, индексы и `NOT VALID`
ограничения. Переименование или удаление legacy-полей до состояния `retired`
запрещено.

## 2. Dual-write

Запись выполняется в таком порядке:

1. разобрать запрос в каноническую доменную команду;
2. один раз выполнить доменную валидацию и расчёт суммы;
3. начать транзакцию и заблокировать изменяемую строку;
4. upsert typed-строки по stable ID;
5. записать совместимую проекцию в legacy-структуру;
6. записать один audit event с before/after и `request_id`;
7. зафиксировать транзакцию.

Нельзя независимо повторять «вторую половину» записи после ошибки. Повторяется
вся идемпотентная команда с тем же command/request ID. Импорты, API и фоновые
задачи используют один и тот же application service, а не собственный SQL.

## 3. Backfill

Worker выбирает строки по tenant и стабильному ID небольшими пакетами. Для
параллельных workers применяется `FOR UPDATE SKIP LOCKED`; checkpoint является
диагностикой, а не единственным доказательством прогресса. После сбоя новый
запуск повторно обрабатывает незавершённый пакет.

Для каждой строки возможен ровно один результат:

- `migrated` — typed-проекция сохранена;
- `already_current` — совпадает stable ID, mapping version и canonical hash;
- `needs_review` — указан детерминированный reason code;
- `failed` — техническая ошибка, пакет откатан и может быть повторён.

Обязательные reason codes: `missing_required`, `invalid_reference`,
`ambiguous_mapping`, `tenant_mismatch`, `invalid_money`, `invalid_date` и
`document_missing`. Исправленная вручную строка возвращается в общий worker;
отдельный непроверяемый путь записи запрещён.

## 4. Reconciliation

Сверка формирует неизменяемый отчёт минимум со следующими полями:

- domain, tenant, mapping version, диапазон stable ID и время запуска;
- legacy total, migrated, already current, needs review и failed;
- отсутствующие и лишние stable ID;
- суммы по году/периоду/категории в точных decimal;
- canonical hash значимых полей и hash/размер связанных документов;
- список расхождений с reason code и ответственным за решение.

Canonical JSON использует фиксированный порядок ключей, нормализованные даты и
decimal-строки. `NULL`, пустая строка и отсутствующее поле не считаются
равнозначными без явного правила mapping.

Cutover разрешён, если одновременно:

1. нет `failed`, отсутствующих или лишних stable ID;
2. каждое `needs_review` закрыто либо письменно принято владельцем данных;
3. количества, денежные итоги и документные hash совпадают;
4. два последовательных запуска на полном объёме дали одинаковый результат;
5. restore-проверка последней резервной копии успешна;
6. владелец данных и технический владелец записали решение в audit trail.

## 5. Cutover

Cutover выполняется для одного домена и tenant-wave:

1. зафиксировать backup ID, reconciliation report ID и версию приложения;
2. включить `shadow_read`, выдержать согласованное окно наблюдения;
3. переключить чтение на typed-источник без изменения dual-write;
4. выполнить smoke-тесты create/update/read/export и повторную сверку;
5. при успехе оставить домен в `typed_read`;
6. legacy-write отключать только отдельным решением после двух полных отчётных
   циклов.

Кэш и фоновые jobs должны получать версию состояния домена; смешивание ответов
из двух источников в одном API-ответе запрещено.

## 6. Rollback

Rollback запускается при потере/дублировании stable ID, расхождении денежных
итогов, tenant leak, неразрешённой ошибке документов, росте dual-write failures
или невозможности сформировать обязательный отчёт.

Порядок rollback:

1. остановить следующий tenant-wave и новые backfill jobs;
2. переключить чтение на legacy для затронутого домена;
3. оставить dual-write включённым, чтобы typed-данные не отстали;
4. инвалидировать кэш и повторить smoke/read/export через legacy;
5. сохранить reconciliation diff, request ID и audit event rollback;
6. устранить причину, повторить backfill и все cutover gates.

Rollback приложения не выполняет down-migration и не удаляет typed-строки.
Восстановление БД из backup допустимо только при физическом повреждении и по
отдельному incident-процессу: обычный логический rollback является сменой
источника чтения.

## Приёмка конкретного backfill

- [ ] migration checksum и upgrade-тест проходят;
- [ ] dual-write transaction и её rollback покрыты тестами;
- [ ] повторный backfill не создаёт дублей;
- [ ] tenant isolation проверена минимум на двух ИТ-компаниях;
- [ ] очередь ручного разбора содержит reason codes без потерянных строк;
- [ ] counts, decimal totals, stable IDs и document hashes сверены;
- [ ] shadow-read не влияет на пользовательский ответ;
- [ ] cutover и rollback проверены на копии production-like данных;
- [ ] зафиксированы backup ID, reconciliation report ID и audit request ID;
- [ ] legacy удаляется только новой миграцией после состояния `retired`.

Существующий `TestWorkspaceMigrationPreservesLegacyData` остаётся базовым
upgrade-тестом: он доказывает сохранность legacy entries, сумм, вложений,
соглашений и аудита. Каждый предметный backfill добавляет к нему собственный
двухисточниковый reconciliation test.
