# Runbook эксплуатации (OPS-12)

Инстанс разворачивается в закрытом контуре, где внешнего мониторинга может не
быть. Поэтому состояние подсистем читается из самой системы, а этот документ
говорит, что делать с каждым показателем.

## Где смотреть

`GET /api/admin/metrics` — один срез по всем подсистемам, доступен
администратору. Возвращает JSON с разделами `timers`, `snapshot`, `storage`,
`audit`, `database`.

```
curl -s --cookie "cybercalc_session=<токен>" https://<хост>/api/admin/metrics | jq
```

Отдельно:

- `GET /api/live` — контейнер жив (без обращения к базе);
- `GET /api/ready` — готов принимать запросы (с проверкой базы);
- `GET /api/admin/logs/export` — потоковая выгрузка журнала с проверкой цепочки.

## Регламентные сроки (`timers`)

| Показатель | Норма | Что делать при отклонении |
|---|---|---|
| `next_deadline`, `days_left` | ближайшая контрольная дата Приказа № 270 | при `days_left <= 14` предупредить ответственных: сроки календарные, выходные их не переносят (ADR-02) |
| `overdue` | `0` | каждая просроченная дата — пропущенный регламентный срок; разобрать по экрану «Отчётность», зафиксировать причину |

Сроки считаются по московским датам на сервере. Если показатель расходится с
ожиданием, сверьте часовой пояс контейнера: смещение клиента на расчёт не
влияет, а смещение сервера — влияет.

## Снимок на 1 мая (`snapshot`)

| Показатель | Норма | Что делать при отклонении |
|---|---|---|
| `sealed` | `true` после 1 мая отчётного года | без снимка Приложение № 4 не формируется (409). Снимок создаётся **только 1 мая** по московскому времени и повторно за тот же год не создаётся |

Если 1 мая пропущено, снимок задним числом не создаётся: это осознанное
ограничение неизменяемости. Решение принимает владелец продукта.

## Хранилище (`storage`)

| Показатель | Норма | Что делать при отклонении |
|---|---|---|
| `documents` / `distinct_blobs` | `distinct_blobs <= documents` | равенство означает отсутствие дедупликации; сильный разрыв — норма (один документ приложен к нескольким мероприятиям) |
| `quarantined` | `0` | файлы приняты при недоступном антивирусе и не выдаются. Поднять антивирус, затем перезалить документы |
| `unscanned` | `0` | исторические файлы, загруженные до появления антивирусной проверки. Проверить вручную |
| `deletion_queue` | близко к `0` | очередь растёт — фоновая очистка не справляется или падает. Проверить журнал контейнера backend на `retention:` |
| `expiring_in_week` | — | документы, у которых на неделе истекает срок хранения. Если они ещё нужны, продлить `attachment_retention_days` **до** истечения |

Файл удаляется с диска только когда исчезает последняя ссылка на него:
содержимое адресуется хешем и может принадлежать нескольким вложениям.

## Журнал аудита (`audit`)

| Показатель | Норма | Что делать при отклонении |
|---|---|---|
| `chain_verified` | `true` | `false` означает нарушенную цепочку: запись изменена, удалена или пропущена. Выгрузка журнала при этом отказывает (409) |
| `chain_problem` | пусто | текст называет вид нарушения и номер звена |
| `records` / `archived` | растут | записи старше срока хранения уходят в архив, а не удаляются |

**Нарушенная цепочка — инцидент, а не сбой.** Журнал не изменяется ни
приложением (нет прав на `UPDATE`/`DELETE`), ни через триггер. Разрыв означает
вмешательство в базу или восстановление из неполной копии. Порядок действий:
зафиксировать номер звена, снять копию базы, не продолжать работу до разбора.

## База данных (`database`)

| Показатель | Норма | Что делать при отклонении |
|---|---|---|
| `reachable` | `true` | `false` — backend не видит базу; проверить контейнер postgres и параметры подключения |
| `latency_ms` | единицы миллисекунд | десятки и сотни — нагрузка или нехватка ресурсов |
| `active_sessions` | — | резкий рост при неизменном числе пользователей — повод проверить журнал входов |

## Частые задачи

**Сотрудник потерял устройство со вторым фактором.** Системный администратор:
`POST /api/admin/users/{id}/mfa-reset`. Второй фактор снимается вместе с кодами
восстановления, все сессии пользователя закрываются, событие попадает в журнал.

**Утрачен доступ системного администратора.** Оператор с доступом к хосту
задаёт `ADMIN_BOOTSTRAP_EMAIL` и `ADMIN_BOOTSTRAP_PASSWORD` и перезапускает
backend: учётная запись создаётся или включается заново с новым паролём, её
прежние сессии закрываются. В журнале контейнера появится строка
`восстановлен доступ системного администратора`.

**Перенос старых вложений в адресуемое хранилище.**
`storagemigrate <dsn> <каталог>`. Команда идемпотентна; код возврата `3`
означает, что остались строки для ручного разбора (файл потерян или его хеш не
совпал) — их перечисляет отчёт.

**Антивирус недоступен, загрузка нужна сейчас.** Осознанно переключить
`SCANNER_UNAVAILABLE_POLICY=quarantine`: файлы будут приниматься, но не будут
выдаваться до проверки. Вернуть `reject` после восстановления антивируса.


## Резервные копии и восстановление (OPS-10, QA-11)

Резервная копия — один шифрованный файл: дамп базы, хранилище вложений и
конфигурация. Создаётся и проверяется командой `backupbundle`
(`backend/cmd/backupbundle`); парольная фраза (не короче 12 символов) хранится
отдельно от копии и от сервера, на котором копия лежит.

```
export DATABASE_DSN='postgres://…' UPLOAD_DIR=/app/uploads BACKUP_PASSPHRASE_FILE=/root/backup.pass
export BACKUP_CONFIG='env=/opt/cybercalc/.env' APP_VERSION=<версия>
backupbundle create  /backups/cybercalc-$(date -u +%F).ccbk   # база + вложения + конфигурация
backupbundle verify  /backups/cybercalc-….ccbk                # расшифровка и контрольные суммы
```

- Дамп базы не ложится на диск открытым текстом; память не зависит от размера
  копии (куски по 1 МиБ). Копия защищена AES-256-GCM с ключом из парольной
  фразы (PBKDF2-SHA256, 600 000 итераций); порча, обрезка и перестановка
  кусков обнаруживаются.
- Восстановление никогда не идёт поверх существующих данных: каталог
  назначения не должен существовать, а при любой ошибке не остаётся ни
  каталога, ни временных файлов.
- Копия, не проверенная восстановлением, копией не считается. Учебное
  восстановление берёт временную базу, возвращает в неё дамп и сверяет с
  манифестом число записей, вложений, строк аудита, применённых миграций и
  голову цепочки аудита, а каждое вложение — с его адресом на диске:

```
export ADMIN_DSN='postgres://…'     # право создавать базы; рабочая база не затрагивается
backupbundle drill /backups/cybercalc-….ccbk /var/tmp/drill
```

Учебное восстановление на новой ВМ проводится этой же командой на чистом хосте;
результат («учебное восстановление пройдено» и список пунктов) записывается в
журнал эксплуатации. Резервируйте отдельно ключ шифрования MFA
(`MFA_ENCRYPTION_KEY`): без него восстановленные секреты 2FA не расшифровать.

## Обновление и откат (OPS-11)

Релиз описывается подписанным манифестом (версия, образы по digest, миграции с
контрольными суммами). Подпись — Ed25519; открытый ключ поставляется с
инстансом, секретный хранится вне серверов.

```
upgradecheck keygen ./keys
upgradecheck release migrations 4.4.1 backend=sha256:… nginx=sha256:… > release.json
upgradecheck sign release.json keys/release.key release.signed
upgradecheck verify release.signed keys/release.pub
DATABASE_DSN=… BACKUP_FILE=… BACKUP_PASSPHRASE_FILE=… DATA_DIR=/var/lib/docker \
  upgradecheck preflight release.signed keys/release.pub migrations
```

Предполётная проверка ничего не меняет и останавливает обновление (код 3), если:
файлы миграций не совпадают с подписанным перечнем; применённая миграция
изменена или её нет в релизе (база новее пакета); порядок миграций нарушен;
нет резервной копии, она не открывается или старше 6 часов; мало места.

Схема БД меняется только вперёд. Откат — это откат образов приложения;
`upgradecheck rollback <подписанный прежний релиз> <ключ>` говорит, сможет ли
прежний релиз работать на текущей схеме: не хватает миграций или они применены
иначе — откат недопустим; есть более новые миграции — допустим, если они только
добавляют (расширение схемы), иначе нужно восстановление из копии.

### Проверка схемы при каждой выкладке

`scripts/deploy-safe.sh` после сборки образа и до любых изменений в работающем
стеке запускает `upgradecheck schema /app/migrations` в контейнере `migrate`
(образ содержит `/app/upgradecheck`). Проверка сверяет применённые миграции с
деревом нового образа: схема новее образа, изменённая применённая миграция или
нарушенный порядок останавливают выкладку (код 3), и стек остаётся нетронутым.
Первая установка (таблицы миграций ещё нет) проходит. Подписанный релиз и
резервная копия проверяются отдельно командой `preflight` выше.

## Автономный пакет (OPS-04)

`scripts/build-offline-bundle.sh <версия> <каталог> <секретный ключ>` собирает
пакет: образы (`docker save`), compose-файл, миграции и подписанный релиз с
перечнем всех файлов. На чистом хосте без сети `offline-install.sh
<release.pub>` сначала проверяет подпись и состав пакета (изменённый или лишний
файл останавливает установку), затем загружает образы и поднимает стек без
обращения к реестру.

## TLS для закрытого контура (OPS-02)

`tlsbootstrap` (`backend/cmd/tlsbootstrap`) готовит сертификаты для хост-nginx:

```
tlsbootstrap ca /etc/cybercalc/ca "Локальный центр"                   # ca.pem поставить в доверенные на рабочих местах
tlsbootstrap issue /etc/cybercalc/ca /etc/cybercalc/tls calc.internal 10.0.0.5
tlsbootstrap import fullchain.pem privkey.pem /etc/cybercalc/tls calc.internal [корни.pem]   # готовый сертификат
tlsbootstrap nginx calc.internal /etc/cybercalc/tls 127.0.0.1:8080 > /etc/nginx/conf.d/cybercalc.conf
tlsbootstrap rollback /etc/cybercalc/tls calc.internal /etc/cybercalc/ca/ca.pem
```

Пара устанавливается только после проверки (ключ подходит, имя покрыто, срок,
стойкость, цепочка до доверенного корня), а действующей становится атомарной
подменой указателя `live`: nginx видит либо старую пару целиком, либо новую.
Хранятся три последние версии для отката. Конфигурация перенаправляет HTTP на
HTTPS (308), допускает TLS 1.2+ и включает HSTS. После замены — `nginx -s reload`.

### TLS внутри Docker с автоматическим продлением

`docker-compose.tls.yml` подключается поверх основного файла и переводит nginx
стека на HTTPS без хост-nginx:

```
export TLS_HOST=calc.internal TLS_CA_DIR=/etc/cybercalc/ca   # каталог с ca.pem и ca.key
docker compose -f docker-compose.yml -f docker-compose.tls.yml up -d
```

Одноразовый `tls-issue` выпускает пару до старта nginx, а `tls-renew` каждые
6 часов проверяет срок и за 30 дней до конца выпускает новую: указатель `live`
переключается атомарно, nginx подхватывает пару при перезагрузке раз в 6 часов.
Тот же сервер принимает 443; HTTP перенаправляется на HTTPS (308), кроме
`/api/ready`, `/api/health` и `/version.txt`, чтобы проверки живости и выкладки
работали. Правила фильтрации и ограничения из `nginx.conf` действуют на оба порта.
Без надстройки конфигурация nginx не меняется. Для перенаправления без номера порта
публикуйте HTTP на 80 (`HTTP_PORT=80`).

Автопродление требует, чтобы ключ центра `ca.key` был доступен сервису продления
(монтируется только на чтение). Если ключ центра должен храниться вне сервера,
выпускайте и ставьте пару вручную (`issue` или `import`), а срок контролируйте:
`tlsbootstrap status <каталог TLS> 30 <хост> [ca.pem]` возвращает код 3, когда до
конца срока меньше 30 дней.

## Задачи по событиям отчёта (SEC-10)

Смена статуса отчёта по соглашению сама ставит и закрывает задачи в диспетчере:
«готово» ставит задачу проверки куратору направления, «проверено» закрывает её и
ставит администратору организации задачу утверждения, «утверждено» закрывает
утверждение, возврат в черновик отменяет открытые задачи. Маршрут выбирает та же
цепочка fallback (ADR-22), а постановка попадает в аудит. Список и история видны
на вкладке «Задачи и эскалации» в настройках.
