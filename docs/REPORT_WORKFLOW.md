# Строгая готовность плана и отчёта

Карточка ведётся по ключу `соглашение + год + plan/fact`. План и отчёт
формирует ИТ-организация: представитель образовательной организации не может
создавать, импортировать или редактировать строки и вложения. Для плана статусы
меняются последовательно: `draft` → `ready` → `verified` → `approved`.
Это ограничение определяется типом профиля, а не ролью: администратор или
модератор с типом `edu_institution` также действует только от назначенной ОО.

Для факта те же технические статусы отражают предусмотренный приказом процесс:
`draft` (готовит ИТ-организация) → `ready` (перечень направлен контрагенту) →
`verified` (ОО/РОИВ согласовал перечень либо оператор зафиксировал согласование
по истечении срока ответа) → `approved`. В статусе `ready` представитель ОО
может только согласовать собственный перечень или вернуть его с обязательным
комментарием. Соглашение сразу с несколькими ОО рассматривает оператор, чтобы
один представитель не мог согласовать данные за остальных контрагентов.

Перед `ready` backend заново проверяет действие соглашения и РОИВ, ответственных
обеих сторон, заданный перечень видов и наличие положительной записи по каждому
виду. Дополнительно обязательны подтверждения условий соглашения и приложения
№ 1 и наличия доказательств. Рассмотрение факта контрагентом фиксируется
отдельным переходом после направления перечня и не может быть заранее отмечено
самой ИТ-организацией. Файлы могут не загружаться: подтверждается их наличие у
ответственного лица.

ТОП ИТ/ИИ не снимает требования сам по себе. Исключение действует только при
наличии другой ОО с утверждёнными в том же году и срезе преподаванием, ООП/РПД,
стажировкой либо практикой с трудоустройством и мероприятием по решению
Минцифры.

Триггеры БД возвращают карточку в `draft` после изменения записи, соглашения,
перечня видов или статуса РОИВ. Представление `entry_eligibility` повторно
проверяет текущие условия при чтении. Поэтому дашборд и экспорт не доверяют
устаревшему флагу: в утверждённую сумму попадает только целиком действующий
комплект. `/api/reports/export` не блокируется неутверждёнными данными: файл
формируется всегда, если в выборке есть записи (иначе `409 нет данных для
отчёта`). Если хотя бы одна запись относится к неутверждённому или ставшему
некомплектным отчёту, итоговая строка получает пометку «Предварительная
выгрузка», а статус и допуск к зачёту выводятся по каждой строке. Жёсткий
отказ `409` действует только для формы Приложения № 4 без запечатанного
снимка факта.

## Создание факта из плана

Кнопка «Создать факт из плана» (вкладка «Факт») вызывает
`POST /api/entries/copy-plan-to-fact` с `agreement_id` и `report_year`;
необязательны `category_code` и `partner_id`. Для каждой записи плана создаётся
запись факта с теми же значениями: права, проверки и расчёт те же, что при
ручном вводе, сумма считается по методике. Фактические затраты и вложения не
переносятся — их подтверждает сам факт. Связь хранится в
`entries.copied_from_entry_id` (миграция 0812): запись плана копируется один
раз, повторный вызов её пропускает, даже если факт уже исправлен. Пропускается
и запись, для которой в факте уже есть запись с теми же значениями, поэтому
полностью одинаковые строки плана дают одну строку факта. Ошибка по одной записи
не отменяет остальные: ответ содержит списки `created`, `skipped` и `failed` с
причинами. Не более 1000 записей за вызов.
