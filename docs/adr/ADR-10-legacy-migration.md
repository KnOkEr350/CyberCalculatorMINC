# ADR-10: Миграция существующих `entries`

- Статус: `ACCEPTED`
- Владелец решения: Data owner
- Дата решения: 22 сентября 2026 года
- Основание: переход ТЗ 4.4 от `entries.payload` к типизированным доменным
  таблицам без остановки действующих пользовательских сценариев
- Блокирует: —

## Контекст

ТЗ 4.4 требует типизированные таблицы, тогда как MVP хранит разнородные поля в
`entries.payload`. Нужен переход без потери данных и без остановки текущих
пользовательских сценариев.

## Рассмотренные варианты

1. Big-bang migration с коротким maintenance window.
2. Dual-write, backfill, сверка, переключение чтения и удаление legacy позже.
3. Read-through adapter с ленивой миграцией записей.

## Решение

Выбран вариант 2: контролируемый `dual-write` с пакетным backfill, сверкой и
поэтапным переключением чтения.

Переход выполняется в следующем порядке:

1. Для каждого домена создаётся типизированная схема и детерминированный
   mapping полей из `entries.payload`. Идентификатор legacy-записи сохраняется
   как стабильный `legacy_entry_id` с уникальным ограничением.
2. Запись сначала проходит единую доменную валидацию, затем в одной транзакции
   сохраняется в типизированную таблицу и в совместимое legacy-представление.
   Частично выполненный dual-write запрещён.
3. Идемпотентный backfill обрабатывает существующие записи пакетами. Повторный
   запуск не создаёт дубли. Неоднозначные или неполные строки не угадываются:
   они попадают в очередь ручного уточнения с кодом причины.
4. Reconciliation job сравнивает количество записей, стабильные ID,
   нормативные суммы, ключевые поля и контрольные суммы канонического
   представления. Расхождения публикуются отдельным отчётом.
5. Чтение переключается по feature flag отдельно для каждого домена только
   после нулевого необъяснённого расхождения. На переходном этапе допускается
   shadow-read с регистрацией различий, но ответ пользователю формируется из
   одного выбранного источника.
6. Rollback переключает чтение обратно на `entries` и не удаляет уже созданные
   типизированные строки. До завершения периода совместимости dual-write
   остаётся включённым.
7. Legacy-write отключается после двух успешных отчётных циклов и отдельного
   приёмочного решения. Удаление `entries.payload` оформляется новой миграцией
   и не входит в backfill/cutover.

## Инварианты реализации

- Новые поля ТЗ 4.4 добавляются только в типизированные таблицы; payload
  получает лишь совместимую проекцию уже типизированных данных.
- Денежные значения сверяются как точные decimal/копейки, без `float`.
- Backfill, ручное уточнение, переключение источника и rollback создают события
  аудита и изолированы по tenant.
- Миграция не меняет stable ID, автора, даты создания и ссылки на документы.
- Любой доменный cutover обратим до отдельного решения об удалении legacy.

## Последствия

Подход требует временно поддерживать два представления и reconciliation job,
зато не требует maintenance window, допускает постепенный запуск доменов и
даёт проверяемый путь отката. Big-bang отклонён из-за риска необратимой потери
неоднозначных payload-полей; lazy migration отклонена из-за непредсказуемого
времени завершения и сложности доказать полноту отчётного среза.
