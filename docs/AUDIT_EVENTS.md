# Контракт событий аудита

`BASE-10` задаёт единый контракт для всех backend-модулей. Новые события
записываются только через `internal/platform/audit` и имеют одну структуру:

```json
{
  "actor": { "type": "user", "id": "uuid" },
  "action": "update",
  "entity": { "type": "entry", "id": "uuid" },
  "old": { "amount": "100.00" },
  "new": { "amount": "120.00" },
  "request_id": "32-hex-symbols",
  "comment": "основание изменения"
}
```

Правила контракта:

- `actor.type` равен `user` или `system`; для `user` обязателен `actor.id`, а
  системное событие не маскируется под пользователя;
- `action` — стабильный машинный идентификатор действия;
- `entity.type` обязателен, `entity.id` допускается не указывать для пакетной
  операции над типом сущностей;
- `old` и `new` содержат снимки значимых полей до и после операции; секреты,
  пароли, токены и содержимое документов в аудит не попадают;
- `request_id` совпадает с `X-Request-ID` HTTP-ответа. Для фоновой задачи
  writer генерирует отдельный идентификатор корреляции;
- предметное изменение и его audit event записываются в одной транзакции.

Миграция `0900_audit_event_contract.sql` добавляет обязательные `actor_type` и
`request_id`, проверяет согласованность системного/пользовательского actor и
индексирует поиск по request-id. Исторические записи получают стабильный
идентификатор `legacy:<audit-id>`.

`GET /api/admin/logs` возвращает канонические поля `actor`, `entity`, `old`,
`new` и `request_id`; точную цепочку можно выбрать параметром
`?request_id=...`. Плоские поля `user_*`, `entity_*`, `old_value` и
`new_value` временно сохранены для совместимости интерфейса v1.
