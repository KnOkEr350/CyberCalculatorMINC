# Одиннадцать экранов ТЗ 4.4

Frontend использует единый registry `frontend/screens.js`, из которого shell строит нумерованное боковое меню, заголовок продукта и маршрутизацию. Рабочая область занимает высоту окна и прокручивается независимо от закреплённых topbar и sidebar.

## Модульная топология

- `frontend/core/store.js` — единственное изменяемое состояние SPA;
- `frontend/core/router.js` — выбор экрана и нормализация его фильтров;
- `frontend/core/screen-loader.js` — кэшируемая динамическая загрузка ES modules;
- `frontend/shell/app-shell.js` — sidebar/topbar/layout без предметного dispatch;
- `frontend/screens/<screen>/index.js` — независимый entrypoint каждого экрана;
- `frontend/screens/shared/` — общие адаптеры экранов одного типа.

Registry хранит путь к модулю вместе с descriptor экрана. Shell не содержит
ветвления по конкретным экранам: он передаёт активный descriptor загрузчику.
Новый экран добавляется отдельным каталогом и записью registry, не меняя router
или shell. Порядок скриптов, уникальность entrypoint, маршрутизация и попадание
каталогов в контейнер проверяются frontend-тестами и CI.

| Экран | Реализация frontend |
|---|---|
| 1. Дашборд | KPI норматива 3%, план/факт/профицит, обязательные чипы ВО, распределение рисков и таблица всех видов |
| 2. Партнёры | Единый маршрут к реестру образовательных организаций либо ИТ-компаний в зависимости от контекста пользователя |
| 3. Преподаватели | Отдельный маршрут, только категория `teachers`, семестровые проверки, реестр и расчёт |
| 4. ООП / РПД | Отдельный маршрут `ood_rpd` с существующей матрицей документов и видов работ |
| 5. Стажировки | Отдельный маршрут `internship`, наставники, часы, формула и документы |
| 6. Практика | Отдельный маршрут `employment_practice` с полями и проверкой срочного трудового договора |
| 7. ТОП-ИТ / ИИ | Отдельный маршрут `top_it`, доступный только для аудитории ВО |
| 8. Школы | Один экран с тремя категориями: ИТ-кружки, повышение квалификации и образовательный контент |
| 9. Решение МЦ | Отдельный маршрут `minc_decision` для мероприятий с ручной подтверждённой стоимостью |
| 10. Отчётность | Конструктор среза, готовность комплекта, регламентные сроки, действующие XLSX/DOCX-выгрузки и Приложение № 4 из неизменяемого снимка; будущие `.pkg` и формы АНО АЦ явно отключены до появления API |
| 11. Настройки | Контекст экземпляра, 3% база N-2, восемь ролей RBAC, безопасность профиля и снимки на 1 мая с SHA-256 снимка и каждого вложения; для главного администратора также пользователи, ОКЗ, хранение и Audit Trail |

Экраны мероприятий используют общий проверенный workspace и backend-метаданные полей, но каждый route ограничивает допустимые категории и аудиторию. Это исключает смешение практики со стажировками и школьного трека с мероприятиями ВО/СПО.

Registry покрыт тестом порядка экранов, уникальности маршрутов и полного распределения категорий. Снимки реализованы отдельным backend-контрактом и отображаются в настройках. Функции, для которых API ещё нет (`.pkg`, Diff Engine, CryptoEngine, шестилистовая форма АНО АЦ), не имитируют успешную операцию и отображаются отключёнными.
