# Стандарт backend-модуля

Каждая новая функциональная область размещается в `internal/modules/<name>` и содержит следующие слои:

```text
<name>/
├── domain/       # сущности, value objects и доменные правила
├── repository/   # контракты хранения и инфраструктурные адаптеры
├── service/      # прикладные сценарии и границы транзакций
├── http/         # декодирование/валидация HTTP, вызов service, кодирование ответа
└── module.go     # composition root: создаёт зависимости и регистрирует маршруты
```

Допустимое направление зависимостей:

```text
server -> module.go -> http -> service -> repository
                       |         |           |
                       +---------+-----------+--> domain

http -> platform/httpx -> platform/apperror
service ----------------> platform/apperror
```

Правила:

1. `domain` не импортирует HTTP, SQL, конфигурацию или другие слои своего модуля.
2. `repository` скрывает конкретное хранилище за небольшими интерфейсами; SQL не выходит в `service`.
3. `service` реализует use cases, принимает `context.Context` и переводит инфраструктурные ошибки в `platform/apperror`.
4. `http` зависит от узкого интерфейса service, не содержит SQL и не отдаёт клиенту внутренние ошибки.
5. `module.go` — единственное место сборки конкретных реализаций. Вложенные пакеты не импортируют корневой пакет модуля.
6. Один модуль не импортирует внутренние слои другого. Межмодульный вызов идёт через явно выделенный публичный контракт.
7. HTTP-контракт сохраняется тестами адаптера; бизнес-сценарии проверяются отдельно от HTTP и PostgreSQL.
8. Новые общие примитивы добавляются в `internal/platform` только если ими пользуются как минимум два модуля или они являются утверждённым стандартом.

## Регистрация маршрутов

Корневой пакет каждого модуля реализует `routing.Registrar` методом `RegisterRoutes(*http.ServeMux)`. Модуль полностью владеет своими HTTP-шаблонами и middleware. Общий `server/routes.go` только создаёт регистраторы и передаёт их в `routing.RegisterAll`; добавлять в него отдельные `HandleFunc` запрещено.

Подключение нового регистратора выполняет владелец интеграционного потока. Предметная команда предоставляет готовый `Module`, его route-contract test и параметры конструктора, не изменяя `server/routes.go` в своей ветке. Повторяющиеся шаблоны маршрутов приводят к немедленной ошибке `net/http.ServeMux` при сборке composition root.

Пакеты `authentication`, `directories`, `planning`, `documents`, `reporting` и `administration` сейчас являются границами владения для существующих handlers. Модуль `okz` реализован полностью по слоям `domain/repository/service/http`. Их маршруты изолированы, а бизнес-логика будет переноситься внутрь слоёв соответствующего модуля без возврата регистрации в `server`.

Эталон — модуль `health`. Он сохраняет действующие endpoints `/api/live`, `/api/ready` и `/api/health`, но разделяет домен, проверку PostgreSQL, прикладной сценарий и HTTP-транспорт.

Чек-лист нового модуля:

- зависимости направлены только внутрь по схеме выше;
- конструкторы принимают зависимости явно, глобального состояния нет;
- service покрыт unit-тестами с fake repository;
- HTTP покрыт contract-тестами с fake service;
- ошибки имеют стабильные `kind` и `code`, а причины не раскрываются клиенту;
- маршруты подключаются только через `module.go`.
